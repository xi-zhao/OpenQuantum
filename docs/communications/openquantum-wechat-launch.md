# 我做了一个开源量子 Agent 工作台，叫 OpenQuantum

预计阅读 6 分钟

> 把量子电路、算法、云后端和科研工作流放进同一个界面，让工具真正成为 Agent 可以调用、过程可以检查、结果可以复核的开放能力。

事情是这样的。

DeepSeek Harness 发布之后，我花了三天，把一个一直想做的想法跑了起来。

我想把量子计算里那些散落在不同仓库、不同云平台、不同文档里的东西，放进同一个工作台。

你可以直接问它一个问题，可以让它分析量子电路，可以查询后端，也可以让它跑一个算法。更重要的是，整个过程都能看见。

这个项目，叫 OpenQuantum。

它现在已经开源了。

把项目跑起来，第一眼看到的是这样。

![OpenQuantum 首页](../images/openquantum-home.jpg)

*OpenQuantum 首页，选择工作区后就可以开始一项量子任务。*

主页保持得很安静。选择一个工作区，默认进入 OpenQuantum 模式，就可以从同一个入口开始对话、调用量子工具，也能随时回看执行轨迹。

说实话，最开始想做这件事，并不是因为量子计算缺一个聊天框。

聊天框已经太多了。

真正让我觉得麻烦的，是量子计算的工具一直很碎。

想处理一条电路，要去找 Qiskit。想确认一个 API 的写法，要翻 Qiskit 文档。想看看 IBM Quantum 的机器，要配 Runtime。想查 IonQ 或国内量子云，又是另一套接口、另一套凭据、另一套理解方式。

如果再往前走一步，想让 Agent 真正帮你完成一个量子任务，事情就更复杂了。

它得知道什么时候该用哪个工具，得拿到正确的参数，得处理权限和凭据，还得把每一步留下来。否则最后屏幕上虽然出现了一个答案，你却不知道它到底做了什么。

这对普通用户不友好，对开发者也不友好。

我自己做量子物理，也长期在做 AI 解决方案。我一直觉得，量子计算现在缺的未必只是更强的算法。

它也缺一个更好用的入口。

一个能把算法、工具、后端、模型和科研工作流组织起来的入口。

OpenQuantum 就是从这里开始的。

它做的事情很直接，把已经存在的优秀工具接进来，再用 Agent 把它们组织好。

底层我选择了 DeepSeek Harness。

我很喜欢 Harness 的一个地方，它会保留 Agent 的执行轨迹。

一段任务里，模型做了几轮判断，加载了什么 Skill，调用了哪个 MCP，工具返回了什么，权限在哪里发生了变化，都可以顺着轨迹看下去。

这对开发 Agent 太重要了。

因为 Agent 真正难调的地方，往往藏在中间那条路里。最后一句话写得再好，也解释不了它为什么走到这里。

于是 OpenQuantum 直接沿用 Harness 的 Agent Runtime，在上面增加量子计算真正需要的东西。

这里面有两类最基础的组件。

一类叫 Skill。

Skill 更像一份给 Agent 的领域工作手册。它告诉 Agent，一种方法适合处理什么问题，什么时候该调用工具，哪些边界不能越过去。

另一类叫 MCP。

MCP 提供真正可以执行的工具。它可以连接 Qiskit，可以查询文档，可以访问量子云，也可以把一个确定性的算法交给 Agent 调用。

两者是分开的。

Skill 管方法，MCP 管执行。

这套分工很重要。社区开发者可以只写一份 Skill，也可以只提供一个 MCP 服务。两边通过开放协议组合起来，社区项目原来的形态也能保留下来。

现在，把 OpenQuantum 跑起来，设置中心里已经能看到这些组件。

![OpenQuantum 量子组件设置中心](../images/openquantum-quantum-settings.jpg)

*量子组件、Skill、MCP 和安全凭据，在同一个设置中心里管理。*

先说最容易直接上手的。

Qiskit Circuits 和 Qiskit Docs 默认开启，而且不需要云端凭据。

前者可以创建、读取、转换和分析 OpenQASM 3 与 QPY 电路，也可以比较不同转译结果。后者可以直接查询 Qiskit API、迁移说明、错误信息和 IBM Quantum 文档。

很多时候，你只是想确认一段电路有没有问题，或者某个 Qiskit 接口到底应该怎么用。

以前是开浏览器、翻文档、复制代码、回来再试。

现在可以直接在同一个会话里问，让 Agent 一边查官方文档，一边调用电路工具。

再往前一层，是量子后端。

OpenQuantum 已经接入 FieldQKit，可以发现夸父、天衍、国盾、腾讯、本源、FieldQuantum 和逻辑比特等国内量子云后端。

你可以查询已经配置的平台，按量子位数量筛选设备，也可以查看拓扑和校准摘要。

这一层默认保持只读。

也就是说，先让 Agent 帮你把可用资源摸清楚，再决定要不要进入真实任务流程。

IBM Quantum Runtime、IBM Quantum AI Transpiler、IonQ 和 Quantum Hardware MCP 也已经有入口。涉及云端任务、费用或设备操作的组件，默认关闭。配置凭据并主动开启之后，再进入对应流程。

Qiskit Gym 也保留在设置里，默认关闭。

我更希望它像一个量子工具架。常用的东西拿起来就能用，需要云端权限的东西清楚地放在那里，研究团队也可以继续把自己的设备和服务加进来。

说到这里，真正让我觉得 OpenQuantum 有点意思的，其实还不是工具数量。

是轨迹。

![OpenQuantum 中的 Harness 执行轨迹](../images/openquantum-trajectory.jpg)

*从用户请求一路看到 Skill、MCP 和工具返回结果。*

上面这张图里，OpenQuantum 正在执行一次量子基态任务。

你能看到 Agent 选择了 `solve_and_validate_ground_state`，能看到 MCP 工具确实被调用，也能看到整个任务跨过了多少轮对话和工具步骤。

这和普通聊天机器人的体验很不一样。

普通聊天机器人给你一个答案。

OpenQuantum 更希望给你一条可以检查的任务记录。

如果结果不对，开发者可以沿着轨迹往回找。是模型选错了方法，是 Skill 的边界写得不清楚，是 MCP 参数有问题，还是外部量子云没有响应。

问题终于有地方可以落。

但量子计算还有一层更麻烦的事情。

工具运行成功，不等于科学结论就一定可信。

一个程序可以正常退出，一次调用可以返回成功，甚至页面上可以出现一串很漂亮的小数。

可这串数字到底对不对？

所以 OpenQuantum 里还有第三类组件，Validator。

Validator 把注意力全部放在一件事上，按已经确定的科学规则检查结果。

为了把这件事跑通，我做了一个很小但完整的参考能力，`quantum-ground-state`。

它处理明确限定的二量子位实 Pauli Hamiltonian，在固定 hamming-weight 扇区里运行无噪声 statevector VQE，然后用另一套独立计算检查能量、态矢、收敛轨迹和数值残差。

注意，这里的计算和验收是分开的。

Agent 负责完成任务，科学验收只认 Validator 给出的检查证据。

只有 Validator 的检查项真的通过，页面才会给出对应结论。

我实际跑了一次。

VQE 得到的基态能量是 -1.85727503 Ha。

独立精确参考也是 -1.85727503 Ha。

两者的绝对能量差，大约是 4.44 × 10^-16 Ha。

所有科学检查通过。

![OpenQuantum 量子基态任务的科学验收结果](../images/openquantum-quantum-result.jpg)

*VQE 结果、独立精确参考和科学检查出现在同一条任务记录里。*

它是一个二量子位、边界非常清楚的参考例子。

但我很喜欢这个例子。

因为它把一项量子能力真正需要的几块东西放到了一起。

有方法说明，有确定性工具，有实际结果，有执行轨迹，还有独立验收。

一条完整的链路。

我一直觉得，科研 Agent 如果想真正进入研究流程，拼的是一整套系统能力。模型有多聪明，只是其中一部分。

还要看工具是否可靠，过程是否清楚，结果能不能复核。

模型负责理解和组织任务，MCP 负责执行，Skill 负责领域方法，Validator 负责把科学规则守住。

各做各的事。

这套结构，也是我想把 OpenQuantum 开源的原因。

量子公司可以把自己的硬件、云服务和数据接口做成 MCP。

高校实验室可以把长期积累的研究流程写成 Skill。

算法团队可以加入新的求解方法，再配一套 Validator 和测试，把适用范围、阈值和证据讲清楚。

甚至一个刚刚起步的开发者，也可以先从一份 `SKILL.md` 开始，把自己熟悉的方法教给 Agent。

OpenQuantum 现在采用 MIT License。

项目里使用的 DeepSeek Harness、Qiskit MCP Servers、FieldQKit 和 Quantum Hardware MCP，则继续使用它们各自的开源许可证。每一项的来源、版本和集成方式，也都放在仓库里公开记录。

我希望这件事能简单一点。

社区已经做得很好的工具，直接接进来。

缺少工作流，就补一份 Skill。

需要确定性执行，就接一个 MCP。

涉及科学结论，再加 Validator。

社区可以沿用已经熟悉的开放协议来扩展 OpenQuantum。

当然，OpenQuantum 现在还是一个很年轻的项目。

目前的版本是 0.4.0，已经跑通 Web 工作台、量子组件设置、Qiskit 工具、量子后端发现、Harness 执行轨迹，以及量子基态的独立科学验收。

后面还有很多东西可以继续做。

更多算法 Skill，更丰富的后端连接，更完整的科研 Artifact，更好的可视化，也包括量子公司和研究机构真正拿去二次开发之后，会长出来的那些我现在还想不到的东西。

说真的，这恰恰是开源最让我兴奋的地方。

一个人做项目，往往会把它做成自己脑子里的样子。

但一个开放项目，如果真的有人愿意拿去用、拿去改、拿去接自己的设备，到那时长出来的东西，可能会远远超过最开始的设想。

量子计算这件事，本来就不应该只属于少数几个熟悉复杂工具链的人。

如果 Agent 能把这些工具组织得更自然一点，如果执行轨迹能让过程更清楚一点，如果开放协议能让更多团队把自己的能力接进来。

那量子计算离更多人，也许就会近一点。

这就是 OpenQuantum 想做的事。

量子计算，就在指尖。
